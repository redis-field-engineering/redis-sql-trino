= Controlled QPF, split and concurrency benchmark

Redis Software is this benchmark's default deployment. Redis Cloud is also a supported target for connector performance testing; its hardware, dataset and storage must be matched when comparing settings.
Redis Open Source is an explicit compatibility target, not the default environment and not a substitute for measuring Software/Cloud QPF.

== Protocol

The controlled run uses one Redis Software database throughout, containing the first 5,000,000 physical ClickBench Parquet rows and all 105 columns.
Ordinal keys preserve duplicates. The source SHA-256 is `78aecd305590b48cc3524ea93010eb0806a415de828478d261617383cd3a2eaf`.
Q3, Q5, Q6 and Q30 use the retained independent DuckDB references, exact integer comparisons and a relative floating-point tolerance of 1e-10 (absolute 1e-8).
Every SQL response page must be consumed; an error, incomplete result or failed health check stops the run without retrying the query.

The matrix is Standard/2x QPF, one/automatic connector splits, and 1/4/8 concurrent SQL clients: 12 configurations.
The eight-connection pool and 1,000-row cursor size remain fixed in both split modes.
Each configuration gets a fresh Trino process and one excluded warmup of each query, followed by three measured rounds.
Each round contains three executions of each query in a deterministic shuffled order: 12 queries per round, 36 per configuration and 432 measured queries overall.
The client pool runs at most the selected concurrency, including the final drain of the fixed workload.
The configuration order is shuffled with seed 20261008; each configuration uses the same per-round query order.
Redis remains running, QPF changes in place, and the harness rejects a Redis shard process restart.
Standard explicitly sets `search-workers` to zero: this Software build retained three workers when only the QPF `active` flag was disabled.
The initial attempt stopped at that configuration gate after 36 correct 2x-QPF queries; those samples are excluded from the complete restarted matrix.
The database's internal routing remains `sched_policy=mnp`, `conns=32` in both modes, isolating the worker-capacity change rather than comparing different proxy-routing settings.

The harness verifies the database's QPF and effective `search-workers` settings through the Software management API, records actual Trino source-driver counts, and checks the exact indexed row count before and after each measured round.
Redis shard CPU seconds are read from each shard process's live Linux counters, using timestamps around each round; retained thread names provide additional runtime evidence.
Linux cgroup v2 counters provide total Redis Software and Trino CPU use, memory use and throttling; those broader counters include each container's service overhead.
Average CPU cores means CPU seconds divided by elapsed seconds, not a percentage of all host CPUs.
One-second memory samples provide a sampled peak rather than an exact high-water mark.
Request, conversion and exact-read metrics can overlap and must not be added to reconstruct latency.

The temporary ARM64 host has 16 physical cores and 64 GiB RAM.
Redis Software gets CPUs 0-7 and a 48-GiB container limit, with a 36-GiB, two-shard database and AOF every second.
Trino gets CPUs 8-15, a 12-GiB container limit and an 8-GiB JVM heap.
Both containers use the same host and 200-GiB gp3 volume at 6,000 IOPS and 250 MiB/s throughout the comparison.
This isolates their assigned CPU cores but shares the host memory subsystem, storage and kernel; it is a development benchmark, not a production topology recommendation.

Throughput is completed queries divided by each measured round's elapsed time.
SQL latency excludes subsequent metrics retrieval; the harness retrieves Trino metrics after the timed round.
Per-query p95 has only nine measured samples per configuration and is descriptive, not a production tail-latency estimate.

== Results

All 432 measured SQL queries returned the complete expected results.
The independent audit re-read every CSV, checked its SHA-256 and value against the DuckDB reference, verified 85 before/after/final index health snapshots, and confirmed that the two shard processes never restarted.
Standard used zero worker threads and 2x QPF used three per shard throughout; no measured round reported Redis or Trino CPU throttling.

The table reports the median throughput of three rounds. Each round executes the same 12-query mix.

[cols="1,1,1,1,1",options="header"]
|===
|Scan mode |SQL clients |Standard QPS |2x QPF QPS |2x / Standard
|One source |1 |0.061 |0.065 |1.05x
|One source |4 |0.100 |0.111 |1.11x
|One source |8 |0.114 |0.143 |1.25x
|Automatic |1 |0.085 |0.130 |1.53x
|Automatic |4 |0.088 |0.143 |1.62x
|Automatic |8 |0.087 |0.139 |1.60x
|===

2x QPF increased throughput in every matched configuration, from 5% with one source and one client to 62% with automatic splits and four clients.
The extra workers matter most when the connector exposes concurrent work: either several SQL queries, multiple scan sources, or both.
This answers the multicore question directly: server-side query workers can make this workload faster, but the gain depends on eligible parallel work and does not apply uniformly to every query.

Automatic splits plus 2x QPF and four clients had the highest measured throughput, 0.143 QPS.
Eight clients did not improve it and increased median query latency.
One source with 2x QPF needed eight clients to reach similar throughput; its median Q3/Q5/Q6/Q30 latencies were 12.16/68.97/55.08/57.61 seconds, versus 7.13/36.76/36.05/30.08 seconds with automatic splits and four clients.
For this workload, start with 2x QPF, automatic splits, eight scan connections and a Trino resource-group limit near four concurrent analytical queries, then retest with the production query mix and latency objective.

For one SQL client, automatic splits plus 2x QPF completed the fixed workload at 0.130 QPS, about 2.0x the 0.065 QPS with one source.
The scan-query medians fell from 20.00 to 10.33 seconds for Q5, 16.81 to 6.82 seconds for Q6, and 16.64 to 6.43 seconds for Q30.
Q3 stayed near seven seconds because its aggregation is pushed down as one Redis operation and therefore retains one Trino source.

Automatic splitting is not universally faster under concurrency.
With Standard QPF, one source outperformed automatic mode at four and eight clients; multiple SQL queries already supplied concurrent scans, and partition overhead added contention without worker capacity to absorb it.
The combination of automatic splits and 2x QPF is what produced the best balance here.

== Server profiling

Separate, untimed `FT.PROFILE` calls retain the pushed Q3 reducers for both worker settings.
These direct calls reproduce the result for this dataset but omit the connector's additional null and precision guards; they are a diagnostic, not the complete SQL execution plan.
The source schema leaves `advengineid` and `resolutionwidth` non-SORTABLE, so these profiles load the underlying hash fields.
With three workers, the two shards report about 3.10 and 3.31 seconds of `Threadsafe-Loader` GIL time within total profile times of 4.28 and 4.49 seconds.
Redis defines this metric as time holding or waiting for its global lock, not solely lock contention; see https://redis.io/docs/latest/commands/ft.profile/[FT.PROFILE].
This is evidence that document loading can limit scaling, not proof that all four SQL queries have the same bottleneck.
Profile timings include instrumentation and are excluded from the SQL latency samples.

https://redis.io/docs/latest/operate/oss_and_stack/stack-with-enterprise/search/scalable-query-best-practices/[Redis's scaling guidance] recommends keeping required return fields in suitable SORTABLE index representations to reduce document loading.
That is a separate schema experiment: preserve exact BIGINT values and original strings, measure added index memory, and rerun correctness checks before adopting it.
This matrix keeps the existing schema and all query semantics unchanged.

== Reproduction

The Linux harness expects a dedicated host with Docker, Python, `redis==6.4.0`, `pyarrow==21.0.0` and `boto3==1.40.45`.
`QPF_ROOT` defaults to `/opt/qpf`; keep this directory private because it holds generated database credentials.
The host must have at least the CPU and RAM allocations specified above.

Stage these inputs before running:

* `hits-5m.parquet`: the exact sample with the SHA-256 above.
* `redis/load.py` and `redis/create.sql` from `benchmarks/clickbench/redis/` for the existing lossless value encodings.
* `create.sql`, `queries.sql` and the Q3/Q5/Q6/Q30 reference JSONs from `benchmarks/issue-135-136/cloud-2026-10-08-pr-5m/`.
* The built connector directory under `plugin/`, with its JAR SHA-256 recorded in `runtime.json`.
* `runtime.json` with `trinoImage` and `redisImage` pinned to their local image IDs, `connectorRevision`, `connectorJarSha256`, and private checkpoint `bucket`/`prefix` settings.
* These scripts in `qpf/`.

[source,console]
----
python qpf/software.py bootstrap
python qpf/start-trino.py --splits 1
# Execute create.sql through Trino once to create the empty hits_5m index.
python qpf/load.py
python qpf/run.py
python qpf/summarize.py /opt/qpf/out
----

`software.py` creates only its named isolated Software container/database and refuses to replace an unrelated cluster.
The loader requires an empty index; use a new environment rather than overwriting prior data.
The run writes sanitized outputs, metrics, health checks and configuration snapshots under `out/`, and checkpoints them into the configured private S3 prefix after each round.
Checkpoints exclude the private connection and management credentials.
Install a bounded cleanup deadline before provisioning resources and delete the temporary host after retaining the results.

The earlier unmatched Cloud comparison remains at `../issue-135-136/cloud-2026-10-08-qpf/`; its resident data and storage differed and it cannot isolate QPF's effect.
The earlier local projection benchmark at `../issue-142/` is a separate dataset shape and runtime.
