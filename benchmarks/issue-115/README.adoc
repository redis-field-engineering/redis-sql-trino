= Issue #115 tuning experiments

Measured October 6, 2026 against the issue #115 fix on base commit `4d2841e`.
Local ARM64 Java 25 and Redis Enterprise Software `8.2.0-78.18` ARM64, whose database loaded Redis/Search 8.6.
Docker allocated 10 CPUs and about 8 GiB of RAM. TPC-H tiny: 60,175 lineitem rows and 15,000 orders. Two background clients.
All runs are sequential, with fresh databases and Trino runners. They are exploratory measurements, not production sizing results.
The sweep uses 3 warmups and 15 timed samples per workload. The repeated baseline and 2x candidate use 5 warmups and 30 samples; the 2,000-row and pushdown-off runs use 5 warmups and 15 samples.
Other containers were observed consuming several CPUs during the later runs. Baseline latency changed substantially, so do not treat cross-run ratios as controlled speedup estimates.

The 2x factor configured `search-workers 3`; the 4x factor configured `search-workers 6`, verified in the database configuration.
Keep the existing one-batch read-ahead default. The two-batch experiment was restored after measuring it; it is not a new connector setting.

Pushdown is enabled except in `pushdown-off`. With pushdown off, `sum_arithmetic` is a SQL aggregation computed in Trino from cursor batches, so its background workload is no longer a server-side global aggregation.

The preferred starting configuration for mixed workloads is factor 2x, four connections, 1,000-row batches and one read ahead. The candidate returned similar aggregation-load lookup medians in its initial and repeated runs. Six workers, eight connections and smaller batches did not show a useful advantage here. The 2,000-row batches improved scans at the expense of lookup latency under scans.

Use `redisearch.aggregation-pushdown.enabled=false` when workers cannot be enabled and interleaving commands is more important than individual aggregation latency and transfer volume.

Reproduce:
[source,console]
----
./mvnw test -Dtest=RediSearchQueryBenchmark -Dair.check.skip-all=true -Dbenchmark.focus=true -Dbenchmark.warmup=5 -Dbenchmark.iterations=30 -Dbenchmark.label=candidate -Dbenchmark.query-performance-factor=2 -Dbenchmark.scan-connections=4 -Dbenchmark.cursor-count=1000
----

For the baseline, use a different label and `-Dbenchmark.query-performance-factor=0`. For the fallback, also add `-Dbenchmark.aggregation-pushdown=false`. Repeat in alternating order on a quiet host.

`results.csv` preserves every timed sample, per-run median/p90, row counts, and scenario settings. The benchmark also writes a `.properties` sidecar for newly reproduced runs. All measured queries returned the same row counts; dedicated regression tests check result values and query plans with pushdown disabled.

Validation: 34 targeted tests passed with the 2x query performance factor, covering config defaults/mapping, enabled and disabled aggregation plans/results, and single-shard/sharded cursor behavior. The 14 config and disabled-pushdown tests passed again with ordinary server defaults and no worker tuning.
