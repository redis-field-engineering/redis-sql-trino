= Exact BIGINT fallback scan: issue #133

The unchanged Q5 SQL is `SELECT COUNT(DISTINCT UserID) FROM hits;`.
This change accelerates its exact scan fallback: Trino still computes DISTINCT over the recovered BIGINT values.
It buffers a cursor batch's HGETs on a private connection and overlaps the next cursor request with the current batch's exact-value reads.
The private connection opens only when an integer may have rounded and closes with the page source, including limited/cancelled scans.
Shared scan connections keep automatic flushing enabled, and cursor read-ahead remains bounded at one batch.

NUMERIC grouping and DISTINCT pushdown remain unsupported for BIGINTs that may round.
On the test server, projected NUMERIC `LOAD id AS raw` still rounded `9007199254740993` to `9007199254740992`.
`LOAD *` preserves the hash text but transfers every field, which is unsuitable for the 105-column ClickBench scan.
A future string/TAG distinct implementation must prove SQL integer identity, NULL exclusion and distributed merging before replacing this fallback.
The patch does not add approximate counts or sum shard-local distinct counts.

== Validation and measurements

The cursor tests cover adjacent integers beyond 2^53, both signs, signed extrema, zero, missing fields, equivalent decimal/scientific spellings, duplicate IDs across two shards, multiple exact columns, multiple cursor batches and early termination.
The SQL DISTINCT result is checked against the explicit expected set; the raw projection checks the exact-read counters.

`hash-read-measurements.json` records a separate local command microbenchmark using Redis Enterprise 8.2.0-78.18 in Docker on macOS ARM.
Each sample issues 100,000 HGETs in batches of 1,000 over 10,000 keys storing `9007199254740993`.
Attempt zero is warmup; the following three attempts alternate buffered/unbuffered order.
Median HGET time falls from 943.84 to 850.87 ms without sharding (9.9%) and from 680.08 to 565.95 ms with the two-shard OSS API (16.8%).
There is sample noise: one sharded buffered attempt was slower. These are command-throughput measurements, not full Q5 timings.

The end-to-end local Q5 comparison is recorded in `sql-measurements.json`.
It scans 100,000 distinct adjacent large BIGINTs on two shards, with cursor count 1,000 and four scan connections.
The reference result is exactly 100,000 in every attempt.
After one warmup, baseline times are 1,759.59 / 1,750.05 / 1,848.64 ms and candidate times are 1,638.11 / 1,555.29 / 1,723.14 ms.
Median time decreases from 1,759.59 to 1,638.11 ms (6.9%). This local comparison does not establish the required full-data speedup.
The report pins the baseline commit and SHA-256 of each changed candidate production source file.
