= SQL, Trino and Redis modernization

This implementation revisits the gaps in https://github.com/redis-field-engineering/redis-sql-trino/issues/185[issue #185].
The Trino 484 / Java 25 baseline is retained; this work adds capabilities and current SPI integration.
Historical unsupported or not-planned decisions are context, not permanent restrictions.

HASH writes resolve physical indexed aliases and preserve all-NULL rows with a reserved marker.
Encoded complex values reject a top-level encoded NULL; nested NULLs remain valid.
Grouping retains Trino execution when stored representations cannot yet be normalized to exact SQL equality.
These restrictions can be replaced by proven normalization or another execution strategy.

== Validation environments

Independent Maven test JVMs own separate Redis Software clusters; `redisearch.test.cluster-label` names their Docker containers and `redisearch.build-directory` isolates build output and reports.
OSS compatibility tests use a disposable container per class; CI configures Redis 8.4 and 8.10.3.
Software suites cover single-shard and OSS Cluster API databases; product tests load the packaged plugin in stock Trino.

Performance assertions compare exact results, plans and source metrics: eligible DISTINCT counts return final aggregates, conditional counts return aggregates, and local TopN loads projected fields for selected candidates.
No new full-data ClickBench timings or comparative speedups are claimed.
Paid Cloud qualification and existing Flex capability issues remain separate from Docker validation.

Validation recorded on November 21, 2026:

* Across the full regression run and final post-pull targeted rerun, the latest per-class reports contain 679 cases, zero remaining failures/errors and 12 expected skips.
* The final normal `package` build passed all static checks and 268 affected/incoming acceptance cases (nine expected skips), including the schema-order fix and cursor-free backslash-key continuation.
* New LIKE, finite grouping, JSON TopN and mixed numeric hydration checks passed on Redis OSS 8.4 and 8.10.3. Software suites cover normal and sharded databases, with JSON ordering under RESP2 and RESP3. CI includes the new execution suites with serialized JUnit.
* Stock Trino 484 loaded the final packaged plugin: 26 product cases passed with zero failures/errors/skips, including escaped/anchored LIKE and nested JSON alias ordering plus exact source filters on both Redis topologies.

Tests used disposable Docker Redis environments. Final combined verification serialized Software provisioning and JUnit execution without changing production timeout, precision or incomplete-result guards.

Work-reduction fixtures:

* Canonical CHAR grouping transfers six groups from 1,200 documents. With an input-count budget too small for 1,050 documents, finite BOOLEAN/CHAR(0) bounds permit two, three, six or nine groups instead of a Trino aggregation scan.
* Anchored LIKE scans transfer 30 matching rows instead of 390; a pushed COUNT transfers one row with no cursor reads. Contains-style patterns retain Trino residuals because Redis contains() truncates at embedded NUL bytes.
* Mixed numeric HASH TopN keeps the same 1,107 source rows, five winners and 15 projected-field reads while coalescing Redis commands from 2,219 to 1,112 and read batches from 61 to 31.
* JSON TopN scans 137 narrow source rows and retrieves five winners through five JSON.GET commands, 15 projected paths and one read batch, with no HASH commands. Modern-path fixtures scan 17 rows and hydrate five winners with 80 projected paths.
* Exact indexed HASH IN constraints on a 1,050-document table permit two or three VARCHAR groups within matching budgets, instead of transferring the filtered documents to Trino for grouping. Products and DISTINCT first-stage keys use the same capped bound; nullable/filter-only, JSON and non-discrete domains remain conservative.

These are exact-result and work-reduction assertions, not full-data throughput claims.


== Ordering and diagnostic acceptance: #180 and #182

The acceptance follow-up adds adversarial HASH and JSON residual predicates that must run before TopN candidate pruning, plus an exact HASH string-filter work assertion.
The canonical guide now separates native numeric ordering, typed HASH/JSON candidate selection and Trino fallback, including supported types, NULL orders, temporal precision and source-versus-winner metrics.

Aggregation, staged DISTINCT and TopN declines emit stateless DEBUG category/reason/action diagnostics.
Configuration-disabled, unavailable-capability and correctness-guard paths remain separate, and literal expression/domain values are omitted from the diagnostic context.
Existing finite grouping bounds and independent precision/protocol checks are preserved.
A cached-count test connects accepted planning statistics to the actual reader's rejection of unsafe growth; cached statistics are not claimed to be snapshots or a hard runtime grouping cap.

Validation on November 21, 2026:

* Normal package checks and 209 selected unit/Software cases passed with no failures, errors or skips. This cohort covers HASH/JSON, single and multiple shards, RESP2/RESP3, aggregation, DISTINCT and finite/domain grouping bounds.
* Four targeted filter-before-ordering cases passed on each of Redis OSS 8.4 and 8.10.3, including JSON under both protocols: eight additional cases with no failures, errors or skips.
* The HTML/PDF guide rebuilt successfully, and git diff --check passed. An independent subagent reviewed eligibility preservation, runtime guard behavior and diagnostic privacy.

These selected acceptance results are a separate cohort from the earlier modernization counts above. They establish correctness and work accounting, without a new full-data performance claim.


== Predicate and ordinary-view acceptance: #179 and #168

Bounded HASH/JSON fixtures compare the same source with connector pushdown disabled for NULLs, empty strings, case, separators, whitespace, controls/NUL, quotes, backslash, Unicode, nullable compounds and LIKE/ESCAPE.
Residual-before-LIMIT, ordering and aggregate checks retain exact SQL semantics. Existing JSON numeric first-match/ANY-match and invalid scalar-shape guards are included in the selected regression cohort.

Ordinary-view tests verify persisted types/catalog/schema, caller-independent source resolution, SHOW/list/query/drop and referenced-table add/drop/recreate/type drift.
Real Trino access-control checks distinguish definer owner authority from invoker source permissions, owner revocation and view/create/drop privileges.
CURRENT_USER is asserted separately as the query caller in both modes, following Trino's contract. Materialized-view implementation remains unsupported and separately tracked in #193.

Validation on November 21, 2026:

* Across the selected Software/unit suites and final corrected view rerun, the latest selected reports contain 44 cases with no failures, errors or skips; the final normal package build passed all eight single-shard/sharded view cases.
* The predicate and view suites passed nine cases each on Redis OSS 8.4 and 8.10.3: 18 additional cases with no failures, errors or skips. CI includes both new suites in that compatibility matrix.
* Workflow actionlint and git diff --check passed. HTML/PDF guide generation was verified after the contract updates.

One initial local Software database activation timed out before SQL assertions; its timeout was preserved and validation used fresh disposable clusters. The results above are selected acceptance cohorts rather than a new full-repository or full-data benchmark claim.
