= SQL query execution: implemented extensions and next steps

This design records the work for issues #175–#182.
It distinguishes SQL that Trino already evaluates from operations translated to Redis.
The acceptance tests accompanying code are the executable contract; the proposals below do not advertise unimplemented features.

== #175: extending the explicit native Search API

The implemented read-only `system.search(table_name, query, schema_name, parameters)` table function returns the table's declared columns and its Redis `__key`.
The analyzer resolves the table and its types before execution and checks underlying column SELECT privileges.
The schema and parameters arguments are optional, preserving existing two- and three-argument calls. Parameters are MAP(VARCHAR, VARBINARY), defaulting to an empty map. Serialized handles preserve an immutable base64 representation; command construction restores exact bytes, and diagnostics redact values. Nonempty parameters conservatively keep source constraints, SQL WHERE, dynamic filters, partitions and keyset paging from changing global native membership. SQL grouping, ordering and limits can run after the native selection; Flex rejects nonempty maps.
The existing cursor, timeout, incomplete-result detection, cancellation and metrics paths are reused.

Typed/vector/geo wrappers and explicit score/distance columns remain future work once their output contracts are defined. Parameter values now bind separately from native query text, including raw vector bytes; the caller chooses the index-compatible encoding and dimensions.
KNN ranking, full-text scores and GEOSHAPE relations need independent tests because their order/score semantics differ.
Acceptance for those extensions requires raw Redis versus SQL comparison for text stopwords/stemming, geo units/coordinates, vector dimensionality/distance, invalid parameters, HASH/JSON and sharded deployments.

== #177: extending exact DISTINCT

Serialized handles represent ordered aggregation stages explicitly. An eligible COUNT over the first grouping-only stage adds a second GROUPBY/REDUCE, for both global and grouped DISTINCT rewrites.
Source presence flags survive the first grouping as internal keys; the second stage sums them to preserve zero for groups containing only NULL distinct values. Redis intermediate NULL group slots still report as present, so testing existence only after grouping would overcount. Empty global input also returns zero.
HAVING stays after aggregation; filters, limits and sorting cannot be silently moved across a stage boundary.
The existing group/document budget and exact count guards remain in force.

Redis documents COUNT_DISTINCT as hash-set based and memory heavy, and COUNT_DISTINCTISH as approximate.
The latter is not a replacement for exact SQL COUNT DISTINCT.
Grouping raw HASH BIGINT text is insufficient: `1`, `01` and `1.0` can be the same SQL integer, while loading NUMERIC doubles can merge neighboring large IDs.
Canonicalization or exact source representation is required before moving those groups to Redis.
A measured memory budget and server cardinality/failure behavior must accompany any wider eligibility; a cached count cannot prevent concurrent growth.

== #178: numeric arithmetic and grouping

Existing integer widening bounds limit every intermediate sum, including before positive and negative values cancel.
Unknown counts or values outside the exact double range cannot simply be enabled.
DOUBLE signed-zero normalization now runs before grouping on a synthetic key; missing inputs stay NULL and source signs remain available to arithmetic reducers.
HASH BOOLEAN spelling and bounded CHAR padding/truncation now use canonical synthetic keys. CHAR normalization examines at most four bytes per code point and is capped at length eight to bound server expression work. UUID parsing, longer CHAR values, optional ISO_DATE offsets and REAL narrowing still require proven canonical translators.
Candidate extensions include exact decimal/integer accumulation in the connector near the scan, typed canonical group keys, and capability-specific server expressions with proof of overflow behavior.
DECIMAL grouping must normalize scale, and arithmetic MIN/MAX must preserve Trino NaN ordering.
Each implementation needs boundary fixtures around 2^53, integer extrema, decimal scale/precision, NaN/infinities, all-NULL groups and multi-shard cancellation.

== #179 and #180: further predicates and ordering

VARCHAR range translation compares loaded HASH strings with quoted string bounds, avoiding numeric coercion.
Tests establish ordering of numeric-looking strings, empty values, Unicode and nullable OR domains; bounds containing controls remain in Trino.
The pipeline comparison saves transfer without claiming an index seek.
Loading a field precedes testing existence, and nullable domains explicitly include the missing-field alternative.

The bounded local TopN strategy operates independently of native Redis SORTBY.
Multiple keys use Trino's typed ordering operators, including exact DECIMAL and floating-point semantics, with memory reservations covering variable-width keys.
Both NULL orders are handled in the comparator. REAL uses this path because different Redis doubles can decode to equal SQL floats and require a secondary-key comparison. DOUBLE also uses it under RESP2 to avoid relying on the precision of intermediate floating sort values; native DOUBLE ordering remains available under RESP3.
JSON now uses deferred single-key JSON.GET projections. Raw replies reuse the scan decoder without converting numbers through doubles, and validate complete reply structure. Validated modern selectors include `$`, ASCII dotted/recursive members, wildcards, quoted bracket members, array/member unions, indices and slices with positive steps. Numeric selectors fit signed 32-bit integers; filter expressions, legacy paths, noncanonical indices and negative/zero steps retain whole-schema fallback. Multi-match paths preserve first-match SQL decoding.
JSON NUMERIC predicates retain an exact Trino residual before TopN, LIMIT or aggregates, with safe native superset prefilters where supported. Native matching is ANY-value, while a path selecting one node may still return an array; neither path shape proves scalar SQL semantics. Nullable predicates retain their existing fallback.
A missing ordering/projected source column in a worker cache causes a targeted table invalidation/reload. Indexed aliases must resolve through refreshed FT.INFO; sampled unindexed HASH VARCHAR fields can use their existing query handles if absent after sampling. Ordinary cache hits keep the configured refresh behavior.
HASH sorts already requiring exact reads coalesce BIGINT and millisecond timestamp recovery into the same HMGET, retaining the narrow single-key-type strategy when no extra exact read is needed.
Benchmarks should report keys scanned, exact value fetches, projected document fetches, cursor batches, heap memory and final rows, not only wall time.

== #181: relational execution assessment

The decision for Trino 484 is to retain joins, windows, complex grouping and mixed unsupported aggregation nodes in Trino.
These SQL constructs already work. The assessment does not add a transparent relational pushdown path.
Eligible filters, projections and single-grouping-set aggregations can still reduce work at the source beneath Trino operators.
The executable contract is `TestRelationalAssessment` and its sharded subclass; link:../../../benchmarks/issue-181/README.adoc[retained bounded measurements and representative plans] record the evaluated cohort and reproduction commands.

[cols="2,3,4",options="header"]
|===
|Operation |Current execution |Feasibility decision
|Same-catalog INNER/LEFT/FULL joins
|Trino Join; eligible source scans can use dynamic filters.
|Keep Trino execution. The connector inherits the SPI's empty `applyJoin`; the Redis aggregate pipeline has no corresponding general relational join operator. A new implementation must prove duplicate multiplicity, unmatched/NULL extension, skew, memory accounting, cancellation and concurrent-read semantics.
|Cross-catalog joins
|Trino Join, even for two catalog aliases pointing to the same Redis endpoint.
|Keep Trino execution. Trino's metadata manager rejects unequal catalog handles before invoking connector join pushdown. This is not a backend endpoint-equivalence check.
|ROW_NUMBER and ordered ROWS/RANGE windows
|Trino Window/RowNumber/TopNRanking, as selected by its planner.
|Keep Trino execution. There is no generic connector window-pushdown hook. A grouped reducer does not preserve input-row cardinality, peer/frame boundaries or partition ordering. A future explicit bounded top-k-per-partition function needs capability/version gating and its own NULL, tie, ordering and memory contract; it is not a general window translation.
|ROLLUP, CUBE, GROUPING SETS
|Trino GroupId and aggregation preserve grouping identity and duplicate grouping sets.
|Keep Trino execution. A single Redis GROUPBY does not encode omitted-key NULLs, GROUPING bits or duplicate set multiplicity. Do not replace one source read with independent aggregate scans plus UNION: those scans can observe different data.
|Mixed supported/unsupported aggregates
|Trino evaluates the entire aggregation node; supported-only nodes can push down independently.
|Retain all-or-nothing translation. Trino's aggregation rule replaces the complete node and requires a returned projection per aggregate. `AggregationApplicationResult` has no residual aggregate list or raw-row side channel. Returning only COUNT while ARRAY_AGG still needs raw rows is not a valid partial translation.
|===

=== Planner and correctness boundaries

The assessment exposed a repeated-projection bug in the two-frame INTEGER SUM window query.
Projection translation now reuses an existing equivalent expression handle across optimizer passes, preserving output expressions and the planner's one-to-one scan assignments; variable-only passes still report no optimization progress.
This repairs planning without pushing the window into Redis.

Trino 484's `PushAggregationIntoTableScan` rule requires a SINGLE aggregation step, at most one grouping set, simple-reference aggregate arguments, no masks, and a direct TableScan source.
The connector additionally requires exactly one grouping set and preserves its existing type, precision, completeness and group-budget guards.
SQL aggregate FILTER becomes a mask in this planner; a comparison such as `x > 5` also needs a projected boolean expression.
General filtered aggregates therefore require more than removing a connector filter check (see #176).

The tests compare complete typed multisets against independent VALUES relations and the same Redis query with connector pushdown disabled.
Fixtures include repeated join keys on both sides, NULL keys, unmatched rows on both sides, real NULL grouping keys, subtotal NULLs distinguished by GROUPING bits, duplicate grouping sets, and ordered ARRAY_AGG in a mixed aggregation.
ROW_NUMBER has a unique final order key; ROWS and peer-sensitive RANGE frames deliberately differ on ties.
Dynamic filtering is disabled in this measurement cohort to isolate leaf aggregation work; production dynamic filtering remains available.
The cross-catalog fixture uses two Redis catalogs over one endpoint and demonstrates the plan boundary, not distributed-network performance.

The fixture is immutable during measured queries.
The connector accepts READ_UNCOMMITTED only: a separate probe changes a value between two ordered reads in one transaction and verifies that the second read sees it; actual catalog queries reject READ_COMMITTED, REPEATABLE_READ and SERIALIZABLE.
Neither the cursor nor follow-up exact reads provide a snapshot, and there is no atomic view across join inputs.
Use quiescent data or an isolated copy for repeatable comparisons.

=== Proven explicit compositions

An explicit preaggregation before a join can return fewer rows while the join remains in Trino.
The measured SQL groups fact rows by the join key first, then LEFT JOINs the dimension; this changes the query's requested grain explicitly and is not an automatic rewrite of an arbitrary join.
The enabled/disabled comparison executes identical SQL in both modes.

For COUNT-only complex grouping, an explicit finest-grain aggregate can retain one source scan:

[source,sql]
----
SELECT g, h, GROUPING(g, h), COALESCE(SUM(n), BIGINT '0')
FROM (SELECT g, h, COUNT(*) AS n FROM rel_facts GROUP BY g, h) p
GROUP BY GROUPING SETS ((g, h), (g), ())
----

Trino retains the outer GroupId/aggregation and its identity bits.
COALESCE preserves COUNT's zero for empty input, where SUM alone returns NULL.
Tests compare this composition with raw COUNT grouping sets, including duplicate sets and empty input.
The inner aggregate must independently satisfy exact grouping-key, COUNT precision and group-budget guards; it benefits transfer only when the finest-grain group count is smaller than the source count.
This count-only evidence does not justify arbitrary SUM/AVG/DISTINCT rewrites: overflow, rounding, NULLs, decomposability and ordered state need separate proofs.
No optimizer rewrite or new connector execution path is introduced by this assessment.
