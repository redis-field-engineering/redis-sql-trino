= SQL query execution: implemented extensions and next steps

This design records the work for issues #175–#182.
It distinguishes SQL that Trino already evaluates from operations translated to Redis.
The acceptance tests accompanying code are the executable contract; the proposals below do not advertise unimplemented features.

== #175: extending the explicit native Search API

The implemented read-only `system.search(table_name, query, schema_name)` table function returns the table's declared columns and its Redis `__key`.
The analyzer resolves the table and its types before execution and checks underlying column SELECT privileges.
Its serialized table handle preserves the native query while normal filters, grouping, ordering and scan partitions are applied.
The existing cursor, timeout, incomplete-result detection, cancellation and metrics paths are reused.

Further work should add a typed parameters argument, typed/vector/geo wrappers, and explicit score/distance columns once their output contracts are defined.
Values need separate parameter binding rather than manual concatenation into native query text.
KNN ranking, full-text scores and GEOSHAPE relations need independent tests because their order/score semantics differ.
Acceptance for those extensions requires raw Redis versus SQL comparison for text stopwords/stemming, geo units/coordinates, vector dimensionality/distance, invalid parameters, HASH/JSON and sharded deployments.

== #177: extending exact DISTINCT

Serialized handles represent ordered aggregation stages explicitly. An eligible COUNT over the first grouping-only stage adds a second GROUPBY/REDUCE, for both global and grouped DISTINCT rewrites.
Source presence flags survive the first grouping as internal keys; the second stage sums them to preserve zero for groups containing only NULL distinct values. Redis intermediate NULL group slots still report as present, so testing existence only after grouping would overcount. Empty global input also returns zero.
HAVING stays after aggregation; filters, limits and sorting cannot be silently moved across a stage boundary.
The existing group/document budget and exact count guards remain in force.

Redis documents COUNT_DISTINCT as hash-set based and memory heavy, and COUNT_DISTINCTISH as approximate.
The latter is not a replacement for exact SQL COUNT DISTINCT.
Grouping raw HASH BIGINT text is insufficient: `1`, `01` and `1.0` can be the same SQL integer, while loading NUMERIC doubles can merge neighboring large IDs.
Canonicalization or exact source representation is required before moving those groups to Redis.
A measured memory budget and server cardinality/failure behavior must accompany any wider eligibility; a cached count cannot prevent concurrent growth.

== #178: numeric arithmetic and grouping

Existing integer widening bounds limit every intermediate sum, including before positive and negative values cancel.
Unknown counts or values outside the exact double range cannot simply be enabled.
DOUBLE signed-zero normalization now runs before grouping on a synthetic key; missing inputs stay NULL and source signs remain available to arithmetic reducers.
HASH BOOLEAN spelling and bounded CHAR padding/truncation now use canonical synthetic keys. CHAR normalization examines at most four bytes per code point and is capped at length eight to bound server expression work. UUID parsing, longer CHAR values, optional ISO_DATE offsets and REAL narrowing still require proven canonical translators.
Candidate extensions include exact decimal/integer accumulation in the connector near the scan, typed canonical group keys, and capability-specific server expressions with proof of overflow behavior.
DECIMAL grouping must normalize scale, and arithmetic MIN/MAX must preserve Trino NaN ordering.
Each implementation needs boundary fixtures around 2^53, integer extrema, decimal scale/precision, NaN/infinities, all-NULL groups and multi-shard cancellation.

== #179 and #180: further predicates and ordering

VARCHAR range translation compares loaded HASH strings with quoted string bounds, avoiding numeric coercion.
Tests establish ordering of numeric-looking strings, empty values, Unicode and nullable OR domains; bounds containing controls remain in Trino.
The pipeline comparison saves transfer without claiming an index seek.
Loading a field precedes testing existence, and nullable domains explicitly include the missing-field alternative.

The bounded local TopN strategy operates independently of native Redis SORTBY.
Multiple keys use Trino's typed ordering operators, including exact DECIMAL and floating-point semantics, with memory reservations covering variable-width keys.
Both NULL orders are handled in the comparator. REAL uses this path because different Redis doubles can decode to equal SQL floats and require a secondary-key comparison.
JSON needs an equivalent deferred document-projection operation and an explicit scalar extraction contract.
Benchmarks should report keys scanned, exact value fetches, projected document fetches, cursor batches, heap memory and final rows, not only wall time.

== #181: relational execution and Trino 484 planner boundaries

Trino 484's `PushAggregationIntoTableScan` rule accepts one grouping set, simple-reference aggregate arguments, no masks, and a direct TableScan source.
Aggregate FILTER is passed as a BOOLEAN Variable; a comparison such as `x > 5` normally needs a projected boolean expression first.
Therefore general filtered aggregate support requires a nullable boolean projection translator, not merely removing `getFilter()` checks.
That translator must preserve three-valued logic and be usable both by scan evaluation and server APPLY expressions.

Same-catalog joins could use connector `applyJoin` only after a proven backend execution strategy exists; Redis Query Engine has no general relational join operator corresponding to that SPI.
Dynamic filtering, exact key lookups, late materialization or connector-side hash joins are possible separate strategies, each requiring a bounded memory and concurrency model.
Cross-catalog joins continue to use Trino.
Windows require partition-local ordering and frame semantics; Redis group reducers do not provide SQL windows.
Possible first workloads are bounded top-k per partition with an explicit table function, while general windows remain in Trino.
Multiple grouping sets can be decomposed into separate server aggregates plus a Trino union, but need snapshot/concurrency semantics and GROUPING identity handling; a direct single GROUPBY translation is insufficient.
